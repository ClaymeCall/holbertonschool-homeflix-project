## Findings

### F1 [high]: AS-07.6 expects a disabled account's old session to be refused, but the design lets it reach the library and acquisition services for up to 15 minutes
- **Documented:** `docs/product/acceptance-criteria.md:103`: AS-07.6, "reuses a session issued before it was disabled" → "protected resources are refused". `docs/product/requirements.md:60`: ACC-10, "A disabled account cannot sign in or use protected resources."
- **Implemented:** `services/library-service/src/main/java/com/homeflix/library/security/TokenCallerProvider.java:23-30` accepts any token that `SessionTokenVerifier` validates. `SessionTokenVerifier.java:70-71` checks only the signature and the expiry, and never reads the account. The acquisition service is built the same way (`services/acquisition-service/.../security/SessionTokenVerifier.java`).
- **Evidence:** the design documents say so on purpose. `docs/architecture/identity-and-permissions.md:221`: "Known limit (R-10, accepted): the library and acquisition services trust a token until it expires, so a disabled account keeps their access for at most 15 minutes." `docs/product/user-journeys.md:105`: the member "loses access when the current session runs out, within about 15 minutes". `docs/risks.md:65` (R-10) says the same. AS-07.6 and ACC-10, as written, do not allow this window.
- **Reproduction (for a human):** on a test stack, sign in as a test user and keep the cookie. As administrator, disable that user (`POST /api/identity/accounts/{id}/disable`). Within 15 minutes, run `curl -s -o /dev/null -w '%{http_code}\n' -b 'homeflix_token=<cookie>' http://localhost:8080/api/library/media`. The design predicts `200`; AS-07.6 expects a refusal. Re-enable the user afterwards.
- **Suggested correction:** unclear which side is right. The accepted decision (R-10, ADR-0009) suggests changing the documents: reword AS-07.6 and ACC-10 to say that sign-in and renewal are refused at once, and that other protected resources are refused when the current token expires, within 15 minutes. The agent does not propose any change to the authentication behavior itself.
- **Confidence:** high

### F2 [medium]: the architecture overview says only the gateway publishes a port, but Compose publishes qBittorrent's peer port
- **Documented:** `docs/architecture/overview.md:20`: qBittorrent "no published port". `overview.md:44`: "Only the gateway publishes a port." `overview.md:78`: "One published port, on the gateway."
- **Implemented:** `compose.yaml:159-161` publishes `${QBITTORRENT_PEER_PORT:-6881}` on the host in TCP and UDP.
- **Evidence:** ADR-0023 (`docs/adr/0023-qbittorrent-peer-port-and-enforced-settings.md`) and the ADR index (`docs/adr/README.md:57`) record that the peer port is published, and `docs/acquisition/torrent-client.md:12` lists port 6881 for peers. `overview.md` does not mention ADR-0023.
- **Reproduction (for a human):** `docker compose config --format json | jq '.services | map_values(.ports // [])'` on a test checkout with a filled `.env`: both `gateway` and `qbittorrent` have published ports.
- **Suggested correction:** change the documentation. In `overview.md`, say that the gateway is the only HTTP entry point, and that qBittorrent also publishes its BitTorrent peer port and nothing else (ADR-0023), in the diagram label and in both sentences.
- **Confidence:** high

### F3 [medium]: the error model says a database outage gives 503, but every service answers 500
- **Documented:** `docs/architecture/error-model.md:109`: "Database down | The owning service answers 503". `docs/api/README.md:19`: "`503 service_unavailable` is possible everywhere."
- **Implemented:** no handler maps a database error. In each `web/ApiExceptionHandler.java`, the catch-all `@ExceptionHandler(Exception.class)` answers `500 internal_error`: identity lines 83 and 94, library lines 114 and 125, acquisition lines 100 and 111. No production class refers to `DataAccessException` or one of its subclasses (a search of `services/*/src/main` for `DataAccess` finds nothing).
- **Evidence:** a request whose repository call fails because PostgreSQL is down raises a Spring `DataAccessException`, which is neither a `ServiceUnavailableException` nor an `ErrorResponse`, so it reaches the catch-all. Related: the acquisition contract lists no `503` for `GET /entries`, `GET /entries/{entryId}` and `GET /downloads` (`docs/api/acquisition.yaml:48-116`), although all three read the database (`catalogue/EntryRepository.java:40`). A branch named `36-e10-database-outage-answers-503` exists on the remote but is not part of the reviewed commit.
- **Reproduction (for a human):** on a test stack, `docker compose stop postgres`, then with an administrator cookie `curl -s -w '\n%{http_code}\n' -b 'homeflix_token=<cookie>' http://localhost:8080/api/acquisition/entries`. Expected by the documentation: `503` with `service_unavailable`. Then `docker compose start postgres`.
- **Suggested correction:** change the code, as issue #36 (E10) plans: map database access failures to `503 service_unavailable` in the three handlers, and add the `503` response to the three acquisition operations above.
- **Confidence:** medium (based on reading the handlers; not run)

### F10 [low]: the API README says lists use `limit` and `offset`, but most list operations have no paging
- **Documented:** `docs/api/README.md:22`: "Lists are plain arrays with `limit` (default 50, maximum 100) and `offset`."
- **Implemented:** only `GET /accounts`, `GET /media` and `GET /progress` take them (`AccountController.java:48-49`, `CatalogueController.java:38-39`, `ProgressController.java:38-39`). `GET /favourites` (`library.yaml:488`, `FavouriteController.java:39`), `GET /roots` (`library.yaml:35`), `GET /categories`, `GET /genres`, `GET /profiles`, `GET /entries` and `GET /downloads` (`acquisition.yaml:48`, `:94`) return whole lists, in the contracts and in the code alike.
- **Evidence:** the contracts and the code agree with each other; only the general convention says otherwise.
- **Reproduction (for a human):** `curl -s -b 'homeflix_token=<cookie>' 'http://localhost:8080/api/library/favourites?limit=1'` returns every favourite.
- **Suggested correction:** change the documentation: say which lists are paged, or that short lists (profiles, roots, genres, entries) are returned whole. Whether favourites and downloads should be paged is a design question for the team.
- **Confidence:** high
